> 状态：已讨论并收敛的 **POC 产品候选方案**；不是商业价值或技术可行性已验证的声明。  
> 范围：跨境电商商品图包制作，先从 TikTok Shop、Temu 运营的相似工作场景探索；各平台发布规则独立确认。

**2026-10-16 阅读说明**：最新产品方向为 **Commerce Image Workspace**，定位是面向跨境电商运营人员的 AI 商品图片制作与修改工作台，见第 7 节。第 1～6 节保留初始两页式原型与首轮验收基线；其中“已完成实验：无”是初始框架时的记录，不代表当前工程没有真实实验。T01～T04 后续工程、真实实验和 Mac mini 内部试用记录继续以 `02_CURRENT_STATE.md`、`03_EXPERIMENT_LOG.md` 及原始 Evidence 为准。本轮不改变当前两页式部署，新方向尚未实现或完成业务验证。

## 1. 当前业务认识与证据等级

| 等级 | 事项 |
|---|---|
| **运营陈述待核验** | 常见制作方式：收集当前商品实拍、Listing/描述、参考设计图，把材料交给 GPT 提炼卖点，再结合风格、场景、文案等要求生成图包。 |
| **运营陈述待核验** | 现有工作存在图包前后不一致、长对话混乱、局部修改不稳定等困扰。 |
| **技术假设** | 将商品事实和每张图的任务范围明确组织，并对单张图片独立修改，可能降低返工；尚未完成对照试验。 |
| **产品决策（POC 候选）** | 采用两页式交互，第一页准备和计划，第二页生图与逐图审核。 |
| **已完成实验** | **无**：当前基础框架不包含真实模型运行证据。 |

## 2. 页面一 — Prepare & Plan

**输入**（允许非必填项与人工补充，不强制创建复杂表单）：

- 当前 SKU 的商品实拍/素材；商品名称、变体信息（如有）。
- Listing、描述、参数、卖点或其他运营持有的来源资料。
- N 张**设计参考图片**；整体风格、场景、语言与业务要求。

**输出**：运营易于阅读和调整的简短结果：

1. 当前商品的核心信息、可用卖点与需要人工确认的关键信息。
2. 每张图片的一条制作计划：`表达目标 / 对应卖点（可不选） / 参考图的设计手法 / 场景与风格要求`。

**原则**：商品事实只能依据当前 SKU 的可靠资料确认；参考图提供设计方法，不自动提供当前商品功能或数字。所谓“产品理解、参考理解、整合规划”是**业务逻辑**，不是必须拆为三个 API 调用。

**交互**：运营可编辑计划，然后进入生图页。计划应简单，不设多层强制审核，也不以冗长 JSON 报告阻断首次生图。

## 3. 页面二 — Generate & Review

- 按逐图计划生成**真实图片**；每张图可看到参考图、简短计划与当前生成结果。
- 每张图两个主要动作：`Pass`（人工接受当前版本）与 `修改`（提交自然语言意见，生成编辑版或重新生成版）。
- 修改只针对所选图片；不得覆盖原始成图，或静默改变其他已接受图片。
- 可查看必要的旧版本；可导出人工通过的图包。
- 只报告真实执行进度，不伪造隐藏思考或模型成功。

## 4. 首轮低成本原型：最小闭环

建议首轮先使用 **1 个真实 SKU + 2 张设计参考图**，不以做完所有产品能力为前提。以下是最小功能验收建议，而非已获得用户验收：

1. 提交商品资料、两张参考图与运营要求；得到可审阅/修改的两张逐图计划。
2. 通过真实模型调用生成两张**实际图片文件**，不接受占位图或模拟返回。
3. 运营 Pass 其中一张，对另一张提交修改意见并获得新版本。
4. 已 Pass 图片的内容保持不变；修改前图片可追溯。
5. 导出通过的图片；保存最少必要的真实运行信息和失败记录。

**不同类型的验收不要混淆**：功能闭环跑通、图片被运营接受、相对现有流程节省成本/时间，是三种不同的结论。

## 5. 最少观察指标

- 成图被采用 / 被拒绝及**原因**；商品外观、卖点、风格、文字问题的具体例子。
- 每张图的重生/修改次数、实际耗时、可获得的模型调用成本。
- 与运营当前做法的粗略对照；样本不足时只写“初步信号”，不宣称已显著改善。

## 6. 不在首轮预建

复杂 Context Engine、C01～C05 串行服务、独立 AI 审图平台、Skill/Agent/RAG、工作流引擎、全面的平台规则合规模块及大规模多用户系统。若真实实验显示缺口，再另行提出最小必要改动。

## 7. Commerce Image Workspace — 2026-10-16 产品方向

**定位**：面向跨境电商运营人员的 AI 商品图片制作与修改工作台。基于现有任务中心和 T01～T04 能力继续验证业务价值；以下是运营反馈对应的候选改进，不是已上线功能，也不预设正式多模式架构。

### 7.1 运营反馈与证据等级

| 等级 | 本次记录 |
|---|---|
| **已观察业务事实（来源：用户汇总的运营试用反馈）** | 运营认为 Prepare & Plan 与 Generate & Review 两页切换不方便；存在上传图片辅助修改的需求；Temu 运营提出高质量商品图重设计需求。这些记录说明体验与需求存在，不证明候选方案有效或节省了多少成本。 |
| **技术假设** | 新增图片参考可以改善商品外观修正；成熟图像模型可以直接完成高质量重设计；单页工作台可以降低操作成本。三项假设均需验证。 |
| **已完成实验** | 本轮没有新增模型实验或结论；既有真实生成、失败、人工反馈和未完成验收继续保留，不由本次需求反馈推定通过。 |
| **产品决策** | 下一轮优先验证 I01 Quick Redesign、I02 Image-guided Editing；I03 Unified Workspace 作为候选 UI 优化方向，在实验结果明确后决定纳入哪些能力。暂不建设正式多模式架构。 |

### 7.2 改进 1：Unified Workspace

**业务问题**：当前 Prepare & Plan 和 Generate & Review 分属两个页面，运营生成图片后经常需要返回上一页查看参考图、商品理解或制作计划，页面切换增加操作成本。

**候选方案**：保留任务中心，进入具体任务后采用单页工作台，划分 INPUT 与 OUTPUT 两个主要区域：

- **INPUT**：商品资料、Listing、描述、整体运营要求、必要的原始图片。
- **OUTPUT**：N 张独立图片制作卡片，每张呈现“参考图 → 制作计划（按需）→ 生成结果 → 修改 → Pass”。

运营应能在同一工作台查看当前图片的计划和生成结果；详细信息与历史版本按需展开，避免全部内容一次性展开造成页面过长。复用现有任务状态、逐图操作及 Evidence，不无故重写 T01～T04。本次不定义详细前端技术架构；I03 待 I01、I02 实验结果明确后再决定具体交互。

### 7.3 改进 2：Image-guided Editing

**业务问题**：当前修改主要依赖自然语言意见，运营需要上传新图片辅助修改。例如，生成图布局基本满意，但商品主体外观不准确，希望用一张更准确的商品照片修正或替换主体，同时尽可能保留其他设计。

**候选方案**：一次图片修改可以使用当前生成图片、自然语言修改意见、新增辅助参考图片及必要的原有商品依据和本张计划。新增图片必须明确用途，例如：

1. 商品外观修正。
2. 设计风格参考。
3. 局部内容参考。

新增图片默认只影响当前图片任务；未经确认，不得自动升级为整个任务的商品事实或全局视觉依据。保留当前图片版本和修改历史，不静默影响其他图片或已 Pass 版本。

正确传递 Context 不代表模型一定能够精确保持所有未修改内容。I02 需用真实模型验证外观修正、布局/风格及文字保持情况，不预先承诺 100% 局部保持；设计参考中的商品信息不能自动成为当前 SKU 的事实。

### 7.4 改进 3：Quick Redesign

**业务需求**：Temu 运营希望上传一组已有商品图片，将其重新设计为 Amazon 常见的高质量电商信息图、场景图和卖点图，提升商业视觉质量、信息层级、排版、场景表现和卖点表达方式。

**边界**：这不是 Amazon 白底主图模式，不是单纯背景替换，也不代表输出自动符合 Amazon 平台图片发布规则；平台发布规则仍须独立确认。

**候选工作方式**：上传 N 张现有商品图片 → 输入整体设计要求 → AI 逐张重新设计 → 运营修改或 Pass → 导出。

该候选方式不强制执行完整商品理解与创意规划，允许按实际任务补充商品依据；这不改变现有部署中已确认计划的生图流程。不得擅自增加未经确认的商品功能、技术参数或宣传承诺。先通过 I01 用 2～3 张真实业务图片验证成熟模型能力，再根据运营接受、耗时、修改成本和实际费用决定是否正式实现该工作模式，不提前开发新的模式页面。
