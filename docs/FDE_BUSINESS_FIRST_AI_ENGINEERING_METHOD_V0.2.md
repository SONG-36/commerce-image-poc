# Enterprise AI / FDE 业务驱动开发方法 V0.2

**日期：** 2026-10-27\
**性质：** 个人长期工程方法与能力建设记录\
**状态：** PROPOSED — 待本人审阅和 Git 归档\
**适用范围：** 企业 AI、Agent、知识增强、多模态 AI、业务自动化及未来其他行业项目

## 1. 长期能力目标

目标不是掌握最多的 AI 框架，而是能够独立完成：

**真实业务调查 → 业务建模 → AI 能力拆解 → 技术适配 → 能力评价 → 工程交付 → 运营反馈与持续改进。**

同时追求两个不同的结果：

- **Business Outcome：** 真正改善用户工作，减少成本、错误、时间或重复劳动。
- **Engineering Capability：** 积累能够迁移到其他企业业务的分析、设计、开发、调试和交付能力。

商业项目成功与个人工程能力增长分别评价。

长期责任遵循已有的三个维度：

- **Product Thinking：** 判断做什么、为什么做、解决谁的问题。
- **Engineering Ownership：** 对方案、数据、状态、失败、成本、验证和交付负责。
- **AI-assisted Implementation：** 合理使用 Codex 等工具提高开发效率，但不把 AI 完成报告等同于个人掌握。

## 2. 企业 AI 开发的六个决策环节

| 环节 | 核心问题 | 应形成的最小成果 |
|---|---|---|
| 01 Task Discovery | 人目前怎样完成工作？真实痛点是什么？ | As-Is 流程、角色、输入输出、痛点及未知事项 |
| 02 Business Modeling | 什么是正确的业务流程？涉及哪些规则、SOP、判断与责任？ | 业务边界、目标 SOP、业务约束及人工确认点 |
| 03 AI Capability Decomposition | 哪些工作值得交给 AI？能拆成哪些可评价的能力？ | Decision Inventory、能力边界、现有能力与缺口 |
| 04 AI / Agent Suitability | 什么应该用规则、普通程序、模型、Knowledge、Skills、Workflow 或 Agent？ | 候选技术比较、必要性分析、风险与取舍 |
| 05 Task Contract & Evaluation | 如何证明 AI 能力在真实业务中有效？ | 输入输出、事实边界、失败标准、基线及评价样本 |
| 06 Engineering & Validation | 如何最小化实现、可靠运行并验证改善？ | 代码、测试、真实运行、人工评价、成本及失败记录 |

这六个环节是**分析与决策检查单**，不是强制串行的六阶段瀑布开发。

原有 FDE 五步循环——Business Discovery、AI Feasibility、Rapid Prototype、Business Validation、Productization——继续作为快速交付的宏观工作方法。

新六环节对其中的业务建模、能力识别、技术适配及验证决策作进一步细化，两者不构成两套互相竞争的方法论。

## 3. SOP 与 AI 技术的适配原则

业务 SOP 描述正确做事的方法，不代表必须实现 Agent。

选择技术时，优先比较：

| 情况 | 优先候选 |
|---|---|
| 条件明确、逻辑稳定、可以直接校验 | 确定性程序和规则 |
| 输入非结构化，但理解任务明确 | 单次模型调用 |
| 需要多个固定的处理步骤 | Workflow |
| 依赖大量外部事实、规范或专业方法 | Knowledge / Retrieval |
| 需要可复用的专业操作程序 | Skills 或明确的工具 |
| 需要根据中间结果动态查询、选择工具、调整步骤或转人工 | 受约束 Agent |
| 事实责任重大、结果不可逆或不确定性无法消除 | 人工审核与授权 |

**Agent 是技术选择结果，不是项目出发点。**

Skills 不等于知识库；Workflow 不等于 Agent；模型输出符合 Schema 不等于业务判断正确。

## 4. AI 能力评价纪律

每一项重要 AI 能力，都要说明：

1. 原来由谁完成什么判断？
2. 当前不使用新技术时的 Baseline 是什么？
3. 预期改善什么具体问题？
4. 新技术增加了什么能力、成本与失败风险？
5. 使用哪些真实案例检验？
6. 什么结果会支持保留、修改或放弃方案？

原则上先用已有模型能力，再通过对照评价决定是否增加知识、Skills、工具和 Agent。

明确区分：

- **Engineering PASS：** 程序按约定执行。
- **AI Capability PASS：** 模型在限定样本上满足评价标准。
- **Business ACCEPTED：** 真实用户愿意接受并使用结果。
- **Production READY：** 可靠性、权限、恢复、部署等满足当前使用范围。

以上状态不能互相代替。

## 5. 工程实施与 Codex 协作纪律

人负责批准目标、范围、技术取舍及最终结果。

Codex 可以负责只读调查、局部实现、测试与证据整理，但不能自行将研究建议升级为开发授权。

开发任务应根据复杂度明确：

Goal、Scope、Non-goals、Interfaces、DoD、Evidence、Rollback、Cost Authorization。

保持最小端到端闭环。遇到故障，先定位可观察失败，再判断是否需要修改架构或引入新组件。

不以提前建设通用平台作为职业能力增长证明。

## 6. 个人反复训练的方法

每完成一项重要业务决策或工程闭环，进行一次简短复盘。

**A. 业务理解**

不依赖 AI，总结真实业务、用户任务、重复判断及痛点。

**B. 技术取舍**

说明为什么选择当前技术，以及为什么不使用另外两种候选方案。

**C. 关键工程理解**

能够独立解释主要数据流、Context、模型调用、状态变化和异常处理。

**D. 证据判断**

能够指出哪些结论已验证、哪些只是推断，以及下一步最小验证是什么。

**E. 可迁移能力**

回答：如果将这个项目的业务换成另一个行业，我能够复用哪些工程分析方法？哪些实现需要重新设计？

每次复盘不必写成长报告；可以把结论追加到已有项目记录。

## 7. 长期能力评估

重点观察六项能力：

- 能否独立还原真实业务流程。
- 能否从业务 SOP 中识别 AI Capability。
- 能否合理判断 Agent 的必要性。
- 能否设计有对照、有证据的 AI Evaluation。
- 能否理解、调试并维护关键 Python 工程链路。
- 能否解释一次成功或失败的技术决策，并说明代价和局限。

**真正的重复学习，是在不同业务问题中反复运用同一套方法，而不是反复阅读相同定义。**

## 8. 文档维护原则

个人方法论只记录可迁移的方法和实践教训。

每个具体项目单独记录：

- 已观察的业务事实和代码能力；
- 当前研究问题及证据；
- 已批准和未批准的决策；
- 实验及工程结果；
- 下一步任务和剩余风险。

对现有事实源做版本化修订，不反复建立相同职责的 Charter、Roadmap 或方法论文档。

**状态术语：** OBSERVED / INFERENCE / PROPOSED / DECIDED / OPEN / UNKNOWN / VALIDATED。

只有经过对应范围的验证，才使用 VALIDATED。
