## 0. 目的、范围与标记

本阶段回答：**三种商品图制作场景究竟需要哪些可复用的 AI / 软件能力？哪些决策必须因场景而异？需要哪些知识、规则与人工责任？** 本文件不回答最终应使用几个 Agent、几个模型调用、哪些类/模块、数据库 Schema 或部署拓扑。这些需要进入 `04 AI / Agent Suitability`，并用真实 Evaluation 验证。

状态用语：

- `DECIDED`：当前已获确认的业务事实、输入权限或人工责任；不是已完成技术实现。
- `OBSERVED / HISTORICAL`：来自既有工程调查或实验的历史观察；须保留适用范围。
- `PROPOSED`：本轮从 Workflow 推导的能力抽象、共享边界或评价建议；待审核。
- `UNKNOWN`：缺少实际样本、源码核对或运营评价，不能擅自推断。

**边界**：当前 V1 专注商品图的生成、修改、审核与交付；不将长期的消费者评论、社媒洞察、音视频生产或通用 Agent 平台提前纳入当前实施范围。Workflow 是业务职责序列，**不是**固定模型调用链。

## 1. 三个场景的业务差异（DECIDED）

前端目标入口为三个选项，但业务分类仍为两种模式：`Quick（A/B 子场景）` 与 `Listing`。

| 比较维度 | Quick-A：同款快速改版 | Quick-B：换主体快速改版 | Listing：商品资料制图 |
| --- | --- | --- | --- |
| 主要输入 | 目标商品图 + 图位参考图；可选要求 | 目标商品图 + 图位参考图；可选要求 | 目标商品图 + 参考图 + 运营手动提交的 Listing / 描述 / 卖点等 |
| 商品关系 | 参考商品与目标商品同款、同外观（业务声明） | 外观不同；运营声明相关规格及卖点适用 | 参考商品关系未统一限定，需依据当前商品资料判断 |
| 最终外观依据 | 实际待售商品图片 | 实际待售商品图片；**全部相关参考商品主体必须替换** | 实际待售商品图片 |
| 商品宣称主要依据 | 同款参考中的适用信息；留意变体与不确定参数 | 运营确认适用的参考信息；不等于参考全部信息 | 运营提供的当前商品文字资料；参考信息必须核对 |
| 参考图作用 | 可用营销信息 + 视觉再设计 | 可用营销信息 + 设计表达；参考外观须替换 | 主要是营销表达与设计参考 |
| 核心制作决策 | 保留有效信息并差异化重设计 | 主体替换、信息保留、适应新外形重新排版 | 商品理解、逐图卖点分配与专业创意规划 |
| 制作前人工计划确认 | 正常任务不强制独立 Planning | 正常任务不强制独立 Planning | 现有业务流程包含逐图计划的运营确认 |
| 最终交付 | 运营逐图审核、修改、选择版本、Pass、导出 | 同左，额外重点检查主体完整替换 | 同左，额外重点检查方案和商品事实一致 |

**共同业务规则**：卖点必须有据、不得改变语义，运营指定必保留信息不能擅自删除；可以按图位选择突出部分适用卖点。尺寸图仅在运营提供**已标注目标商品真实尺寸**的白底尺寸素材时制作，未提供即不制作。实际产品图决定外观，生成成功不等于业务验收成功。

**E0 输入增量（2026-10-28 / USER-CONFIRMED，工程待实施）：**

- 三个工作入口共享基础商品/参考上传与图位关系：任务内商品素材共享，`product` / `reference` 角色分离；图位采用 `main`、`dimensions`、`comparison`、`selling_point`、`scene`，保留主要参考绑定、启用状态、可选逐图要求和逐图尺寸。当前未实现完整商品素材子分类，不把白底、细节、配件、包装等候选名称当作既有分类系统。
- 当前图位类型、制作目标和对应参考是 **S3 参考适配 / S5 制作判断**的输入；共享分类不合并 Quick-A / Quick-B / Listing 的事实权限，也不改变既有卖点取舍规则。
- 卖点/场景按需动态 N，主图/尺寸/对比各 max1，无固定业务总数。**S6** 需保持每个图位的稳定身份、顺序、参考/商品角色、要求、尺寸和版本可追溯；商品素材张数不决定输出数，N 不等于每次生成必须发送 N 张参考。
- Listing 多图位 Planning 保留原有人工确认，并维护图位—参考 ID—逐图计划—确认版本的兼容关联。全量 Planning 的 Context、参考数量和输出预算是技术容量问题，不承诺任意 N 一次完成。本增量不新增能力编号、独立模型服务或强制 Agent。

## 2. 横向能力地图：共享什么，不共享什么（PROPOSED）

本阶段沿用 S1～S6 六个能力代号，另将现有生产闭环列为基础设施能力（G/R/E），避免把全部业务活动统称为“AI Agent”。

| 能力 | 共用的能力目标 | Quick-A 的重点 | Quick-B 的重点 | Listing 的重点 | 共享结论 |
| --- | --- | --- | --- | --- | --- |
| **S1 商品理解** | 识别商品外观及可用属性，并暴露不确定性 | 同款/变体一致性、原貌保留 | 目标主体身份、与参考商品可见差异 | 图片与 Listing / 描述 / 卖点结合，发现明显冲突 | **部分共享**；事实输入策略不同 |
| **S2 参考图理解** | 识别文字、卖点、构图、信息层级、营销表达、风格和场景 | 参考内容及差异化空间 | 参考商品主体、局部细节及营销表达 | 设计意图与参考宣称的区分 | **高度共享**；模型原生多模态优先作基线 |
| **S3 参考适配与事实权限** | 判断什么能借鉴、能宣称、应替换或应交人工 | 同款信息的适用性与变体差异 | 相关声明可继承的信息，以及全部主体替换边界 | 参考宣称必须有当前商品资料支撑 | **分析框架可共享，业务决策规则不可混用** |
| **S4 平台 / 地区规则适用** | 根据明确的站点、图位、语言、品牌要求获取适用约束 | 差异化及本地化要求 | 替换后的图位与平台要求 | 内容表达及发布要求 | **按需共享**；无来源不宣称已核实合规 |
| **S5 专业制作决策** | 根据商品事实、营销目标、参考设计组织视觉方案 | 卖点聚焦、风格/版式重设计 | 换主体后重构构图、特写、引线、信息卡 | 逐图表达目标、卖点分配、创意规划 | **专业知识可共享，策略必须场景化** |
| **S6 Context Engineering** | 将本次任务有效事实、图片角色、设计决定和约束可靠交给 Generation | 避免将不同 SKU 资料混入 | 严格区分目标外观与参考设计 / 宣称 | 严格使用当前资料与已确认的计划版本 | **原则与基础设施可共享，组装策略不同** |
| **G/R/E 生产与治理** | Generation / Review / Evidence / 版本 / 导出 | 共同复用 | 共同复用，增设替换验收重点 | 共同复用，增设计划一致性验收重点 | **现有工程基础候选复用**；业务效果待验证 |

### 2.1 建议的逻辑关系（非部署架构）

```text
                  三个用户选择的业务入口
           Quick-A   |   Quick-B   |   Listing
                         |
          已确认的场景事实权限与制作约束
```

## 3. 六类能力的最小业务契约（PROPOSED）

以下“输入/输出”描述业务需要看到或能复核的结果，**不是新增 API、JSON Schema 或数据库表的实施规格**。

### S1｜商品理解与事实边界

- **业务问题**：什么才是当前待售商品？外观有哪些不可改变的特征？哪些文字宣称已有依据，哪里存在变体/资料冲突？
- **依据**：目标商品图片；Quick 的场景声明与适用参考信息；Listing 的当前运营资料。
- **最低结果**：目标商品视觉依据、可用商品信息及其来源、明显冲突、证据不足之处。
- **分场景策略**：Quick-A 不凭“外观相同”独立认证参数；Quick-B 不把参考商品的品牌和配件视为同规格事实；Listing 出现**文字与商品图明显冲突**必须指出并请运营确认，不能任选一边自行改写。
- **失败风险**：SKU 混杂、只看图片推断不可见功能、忽略冲突、把运营声明伪称为独立验证。

### S2｜参考营销图理解

- **业务问题**：参考图实际表达了什么、使用了什么设计方法？
- **依据**：目标图位的主要参考图及其可读文字、视觉结构。
- **最低结果**：营销主张与文案摘要、图文关系、构图/信息层级/风格、参考商品主体与局部元素、看不清或有歧义的内容。
- **共享价值**：三个场景都需要；可用原生多模态模型作为能力基线，再比较专业指令或 Skill 的增益。
- **失败风险**：识别数字错误、错把视觉氛围当商品功能、遗漏局部商品主体、过度推断设计意图。

### S3｜参考适配、信息继承与替换边界

- **业务问题**：参考图中的哪些信息能被使用？哪些必须替换？什么情况应建议更换参考？
- **依据**：S1/S2 的可追溯结果、场景选择、运营明确要求、目标图位。
- **Quick-A**：允许沿用同款且适用于目标型号/变体的参考信息；外观保持真实，视觉表达重新设计。
- **Quick-B**：允许使用经运营确认适用的参考卖点/参数；**参考图中所有关联的不同外观商品主体均须替换或合理移除**，包括局部特写与场景；包装、品牌、专属配置不得自动继承。
- **Listing**：当前商品文字资料是主要宣称依据；参考新增卖点/参数需要资料支持；无法支持时不能静默加入方案。
- **最低结果**：可用/不可用/待确认的信息边界、需要保留的内容、需要替换的视觉元素、冲突与换参考建议。
- **失败风险**：Quick 场景误删适用卖点；Listing 误继承参考商品宣称；Quick-B 主体残留或外观混合。

**核心结论**：S3 能共享“判断问题与记录结果的方式”，**不能**共享一条不区分场景的“参考信息全部保留”或“参考信息一律不能继承”规则。

### S4｜平台、站点、图位和语言规则适配

- **业务问题**：当前指定渠道、市场、图位或品牌要求，对内容和视觉有哪些真实约束？
- **依据**：运营明确指定的目标、可信且注明来源/版本的规则、已经确认的品牌要求。
- **最低结果**：本次适用约束、来源与有效性边界、尚未核实的规则。
- **执行边界**：不是每次任务都必须联网查政策；运营未指定渠道时不能虚构平台要求；“视觉上已差异化”不等于发布合规。
- **失败风险**：凭模型记忆杜撰最新平台规则、不同渠道规则混用、将建议包装成法规结论。

### S5｜专业商品图制作决策

- **业务问题**：为什么这张图选这些卖点？如何借鉴参考的设计方法，并在保持真实的条件下制作出有效的画面？
- **依据**：S1～S4 适用结果、图位目标、运营必保留要求、专业设计方法。
- **Quick-A 重点**：选择部分适用卖点作为重点，调整构图、视觉层级、风格与文案表达，避免改坏商品或几乎原样复制参考。
- **Quick-B 重点**：依据新主体轮廓与结构调整构图、比例、特写、引导线和信息卡，不为适应旧版式扭曲商品；卖点取舍沿用 Quick-A 原则。
- **Listing 重点**：根据商品资料规划每张图的目标、卖点、文案、场景、视觉布局和风险，并供运营审核确认。
- **最低结果**：单图可执行的制作方向，以及选用卖点的依据、需保留约束和待确认问题。
- **知识候选**：构图与视觉层级、商品摄影与材质表现、文案可读性、图位方法、营销表达；何时采用知识检索或 Skill **待实验比较**。
- **失败风险**：规划泛泛、卖点分配重复、复杂版式文字失真、好看但不卖货、脱离商品实况。

### S6｜Context Engineering 与输入一致性

- **业务问题**：Generation 实际拿到的图片和指令，是否完整、正确地体现当前场景的事实权限和制作决定？
- **依据**：当前 Task/图位素材、对应版本、运营要求、已确认事实及方案（Listing）、参考使用边界。
- **最低结果**：可以追溯的有效输入角色、商品视觉依据、允许的宣称、设计参考、硬性约束和本次版本。
- **场景差异**：Quick-A 防范变体与混入；Quick-B 强制突出“目标商品外观 vs 参考设计”的角色分离；Listing 必须使用运营已确认的计划与对应商品资料版本，避免过期方案。
- **能力属性**：优先考虑确定性组装、状态/来源检查和记录；模型可辅助理解与表达，**不代表 S6 必须是一个 Agent**。
- **失败风险**：参考主体被当目标主体、错误事实进入生成请求、上下文过载、旧版计划误用、事后无法复现。

## 4. 商品事实、设计参考与人工授权的统一边界（DECIDED → PROPOSED 抽象）

需要清楚区分至少五种信息角色：

| 信息角色 | 权威与来源 | 三场景共用约束 |
| --- | --- | --- |
| **Visual Truth** | 当前实际待售商品图片 | 最终商品结构、轮廓、可见配置以此为准；图片未拍到的部分不能自行补造事实 |
| **Claim / Specification** | Quick-A：适用同款参考信息；Quick-B：运营确认适用的信息；Listing：运营手动资料 | 不能凭参考视觉相似推断全部参数；明显冲突须暴露；业务声明不等于独立检测 |
| **Design Reference** | 每图位运营选择的营销参考图 | 可借鉴风格、布局和营销方法，不等于自动继承其他商品外观或所有宣称，也不等于拥有素材授权 |
| **Operator Constraints / Approval** | 模式选择、必保留信息、制作要求、计划确认、最终 Pass | 不得静默删除必保留信息；争议事实由运营确认；只有人工通过版本才可当最终成果 |
| **Platform / Brand Rules** | 当前渠道/站点的可信来源及运营已确认要求 | 适用时按来源使用；无证据不自动承诺平台合规 |

**尺寸图共同硬规则**：必须先有已标注真实目标商品尺寸的白底商品尺寸素材，否则不制作此图位。参考图里的数字和模型视觉估测不能替代。

**权限与结果的区别**：有权沿用某类参考信息，不等于可以无条件沿用每一个数字；判断方案正确，不等于成图真实执行；生成完成，不等于运营已 Pass。

## 5. 共同能力与场景专属决策的边界（PROPOSED）

### 5.1 有理由共享的能力

1. **参考理解基础**：图中文字、营销结构、视觉语法、商品/场景元素辨识。
2. **来源与冲突表示方法**：记录“来自哪里、运营确认了什么、还有什么未证实”，但不混淆不同模式的事实权限。
3. **专业制图知识**：设计构图、信息组织、图位表达、视觉清晰度及用户审美判断方法。
4. **指定平台的规则获取/应用**：有具体平台和来源时按需调用，不默认全面合规自动化。
5. **Context 组装基础与 Evidence**：素材角色、版本、有效输入、模型响应、逐图审核修改记录。
6. **现有生成和审核闭环**：Generation、Review、Revision、Version、Pass、Export 的复用方向。

### 5.2 必须保留不同策略的部分

- **Quick-A 策略**：同款参考信息适用性、原貌保留、差异化程度。
- **Quick-B 策略**：运营指定外观不同且信息部分适用、目标主体全域替换、视觉重排、替换完成度检查。
- **Listing 策略**：运营手动商品资料优先、参考卖点不得未经核对自动继承、商品图与文字矛盾需运营确认、逐图制作计划人工确认。

**不要将“逻辑可复用”直接等同于“现在必须抽一个统一 Python 模块、统一 Planning 接口或通用 Agent”。** 共享代码的边界要在真正的任务契约、实现成本与 Evaluation 中决定。

## 6. 人工责任与异常分流（DECIDED / PROPOSED）

| 业务事件 | 可由模型 / 程序辅助 | 不可代替的人工责任 |
| --- | --- | --- |
| 选择 Quick-A、Quick-B 或 Listing | 程序按入口应用相应约束 | 运营明确选择并提供真实输入 |
| 商品信息与图片明显矛盾 | AI 指出冲突及证据缺口 | 运营确认商品事实；不允许 AI 自行任选一方 |
| 参考营销信息部分不适用 | AI 标记原因、提出替代设计或换参考建议 | 运营决定关键卖点和是否换参考 |
| Quick-B 主体替换 | 模型执行生成，可提出核对与异常提示 | 成图中参考主体残留不得被直接当作合格；运营最终审核 |
| Listing 逐图方案 | AI 形成可解释的候选方案 | 运营审核、确认或修改后再按确认方案生成 |
| 最终成图及版本 | 系统支持逐图对比、修改、版本保留 | 运营决定 Pass 和交付版本 |

常见异常原则：**确定性资料缺失**（例如尺寸图素材未提供）按业务规则跳过；**事实冲突或关键不可辨认**转人工核对；**画面质量和生成服从问题**留 Evidence 并支持修改/重生；**参考核心表达不适用**解释原因，建议运营更换，而不是擅自编造卖点。

## 7. Knowledge / Rules / Skills / Workflow / Agent 的候选定位（PROPOSED，非架构批准）

| 手段 | 最可能解决的问题 | 当前判断 | 不应承担的责任 |
| --- | --- | --- | --- |
| **原生多模态模型** | 商品/参考理解、创意判断、单图生成 | **Model-first 基线**；先看真实质量 | 独立认证不可见的商品参数或平台合规 |
| **确定性 Rules** | 选择模式、尺寸前置条件、图位限制、必保留约束、版本和审批状态 | 对明确硬规则更适合先使用可解释约束 | 代替专业审美或复杂参考理解 |
| **Knowledge（专业知识）** | 商品图构图、营销表达、图位方法、视觉层级、地区表达经验 | 可作为跨场景共享候选；需比较增益 | 自动成为未经证实的商品事实来源 |
| **Skills（方法 / 工具封装）** | 重复、明确的制图 SOP、特定质量问题的可靠处理 | 是否优于原生模型 **待证据验证** | 强制每张图调用、以存在 Skill 代替业务合格 |
| **固定场景 Workflow** | Quick 简洁路径、Listing 人工计划确认、可预知异常分流 | 保留三场景业务差异，优先清晰可靠 | 把七项业务职责机械拆成七个模型节点 |
| **Agent（动态决策 / 工具选择）** | 在不确定时选择查证、检索专业方法或工具，并在约束下多步处理 | **OPEN：只有实际复杂度与增益成立才引入** | 擅自扩大事实权限、取消人工 Pass、无边界自主发布 |
| **程序化 Context / Evidence** | 来源、版本、一致性、输入快照和结果追踪 | 很可能是共同可靠性基础 | 假装 Context 正确就证明图片正确 |

此处不选定 LangGraph、Agents SDK、RAG 框架、PS 或其他供应商，也不新增 Skill 仓库。能力是否值得拆分，必须由场景、质量、返工与成本证据驱动。

## 8. 现有工程与历史研究证据（OBSERVED / HISTORICAL）

- **已知工程基础**（按此前 Codex 只读报告）：现有 Quick V1 有共享商品素材、图位参考关联、生成、单图修改、版本、人工 Pass 和 Evidence；Quick 正常路径没有强制独立 AI Planning。Listing 已有商品资料输入、AI Understanding / Planning、运营逐图计划确认及后续生产审核链。**不能据此宣布新业务语义或质量已实现。**
- **Quick-B 历史失败**：曾出现要求替换主体而生成结果保留参考商品的情况；可作为回归样本，但根因属于 `UNKNOWN`（输入角色 / Context / 指令 / 模型执行 / 素材不足等都需要证据）。
- **历史 Quick A/B 试验的适用性限制**：当时共同条件错误地禁止沿用任何参考参数和卖点，不符合后来确认的 Quick-A/B 真实业务语义；不能用它直接证明当前业务下某种 SOP、Skill 或 Agent 的增益。
- **旧 C02 参考理解的模型/Skill 对照**：此前有模型原生理解与附加 Skill 的少量实验，但人工质量复核不足；不构成“Skill 无用”或“必须使用 Skill”的结论。
- **当前 UNKNOWN**：三场景真实接受率、返工原因、商品细节保真、专业决策质量、有效图片时间/成本、各场景实际样本分布、S1～S6 如何以最少调用可靠完成。

## 9. 后续 Evaluation 所需的最小证据（PROPOSED；不在本阶段执行实验）

| 样本 | 优先验证的硬性条件 | 优先评价的质量表现 |
| --- | --- | --- |
| **Quick-A 真样本** | 当前商品外观/型号一致；适用参数不失真；必保留卖点不丢 | 差异化程度、信息层级、成图可读性 |
| **Quick-B 真样本** | 参考商品主体、特写与场景关联商品完整替换；无混合结构；沿用信息仍适用 | 新外形下构图合理性、视觉质感与文案表达 |
| **Listing 真样本** | 商品资料为主要宣称依据；图片-文字冲突被提示；计划经运营确认后才生成 | 卖点分配、参考适配、计划与成图一致性 |
| **跨场景共同记录** | 图位/版本/输入来源正确；尺寸条件遵守；无未经批准的最终 Pass | 运营接受/拒绝理由、修改次数、人力耗时、最终可用图片成本 |

建议在评价时至少区分：**理解错误、信息权限错误、制作决策错误、Context 组织错误、Generation 服从/保真错误、审核遗漏**。同一张失败图片的归因应基于实际输入和运行 Evidence，不靠猜测。暂不设置凭空估计的接受率、延迟或成本阈值。

## 10. 交给 04 AI / Agent Suitability 的具体问题（OPEN）

1. **基础形态比较**：维持明确的 Quick-A / Quick-B / Listing 场景 Workflow + 共享能力，还是添加统一的动态 AI 决策/编排层？是否有证据需要两者混合？
2. **模型调用边界**：S1～S5 哪些能在一次多模态理解/规划中可靠完成；哪些场景确实需要检索、外部工具或多轮验证？
3. **Knowledge 与 Skills 增益**：共享制图知识是否提高可用图质量/减少返工；Skill 的成本、延迟、复杂度是否值得？是否只针对特定图位或疑难问题启用？
4. **硬规则与智能判断**：哪些应该由确定性逻辑保证（例如模式、尺寸、版本、必保留），哪些需模型语义判断（参考理解、视觉规划）？
5. **Agent 使用门槛**：只有在需要根据中间观察动态选择知识、工具或下一步时，才比较 Agent 与固定 Workflow；如何限制事实权限和人工确认边界？
6. **生成质量与责任**：如何在不重建 Generation 的前提下验证 Quick-B 全域替换、Listing 已确认计划与实际输出一致？
7. **共享实现时机**：先以少量真实场景建立质量、时间、成本基线，还是已有充分证据可抽象共享组件？避免先做通用平台。

初步技术倾向（`PROPOSED`，非最终决策）：**保留业务入口及场景规则；共享基础理解、专业知识和 Context / Evidence 原则；对于动态查证或工具选择需求有证据时，再局部引入 Agent。** 不能将这句话当作已批准的系统架构。

## 11. 03 阶段结论与进入下一阶段条件

**已形成的候选结论**：

1. 三种业务场景确有可复用的 S1～S6 基础能力，但**相同能力不等于相同事实权限或相同制作策略**。
2. **S2 参考理解**是最明显的跨场景共享候选；**S3 适配规则**是最不应强行统一的部分；**S5 专业制作方法**是值得重点验证的共享 Knowledge 候选。
3. **S6 Context** 更适合优先按来源、版本及场景规则进行可靠组装，不应先等同为 Agent。
4. 现有 Generation / Review / Evidence 是应优先复用的工程基础，但其存在**不证明**新业务质量达标。
5. Agent 是否必要、出现在哪个决策环节，属于后续 04 阶段的开放问题。

**本阶段可以进入评审，但尚未批准 Coding。** 下一步先确认本能力地图与三条 Workflow 是否一致，再对固定流程、共享 AI 决策层、受约束的混合形态进行成本/风险/收益比较，形成 04 阶段的架构建议。审批后再进入 Task Contract、Evaluation 与最小工程增量。
