# V1 商品图 AI 系统实施契约 V0.1

**项目：** `commerce-image-poc`\
**阶段：** 05 Task Contract + Evaluation\
**日期：** 2026-10-28\
**状态：** `PROPOSED / IMPLEMENTATION NOT AUTHORIZED`\
**目标：** 在现有系统基础上实现三个工作模式的真实业务闭环。

建议路径：`docs/05_TASK_CONTRACT_EVALUATION/V1_IMPLEMENTATION_CONTRACT_V0.1.md`

业务依据为 [Business Baseline V0.3](../02_BUSINESS_MODELING/V1_BUSINESS_BASELINE_V0.3.md)。既有自主度修订保持不变；本次仅在 P0-01 补充 E0-R01 共享输入与 E0-R02 动态图位的要求和验收，不改变 P0-02～P0-05、原业务质量底线及 E0～E5 基本顺序；架构候选中的演进边界不构成当前 Coding 授权。

## 1. 一期交付目标

让运营可以选择 Quick-A、Quick-B 或 Listing，提供对应商品资料和参考图，得到符合商品事实及目标图位要求的候选图，并能够修改、确认、Pass 和导出。

一期完成标准不是模块数量、单元测试数量或模型 API 调用成功，而是**实际业务案例能够走通，并经过运营人工验收**。

一期属于低自主度 AI 应用工程：核心交付仍是三个工作入口、业务事实权限与关键 Rules、AI Understanding / Decision、正确的 Context Engineering、Generation / Review / Evidence 及真实运营验收。内部仍保留 Quick（A/B 子场景）与 Listing 两种模式；不开发三套独立系统。

## 2. 开发原则

1. 优先修正当前工程与已确认业务规则的差异。
2. 最大限度复用已有 Task、Planning、Generation、Review、Evidence。
3. 不为了三种场景创建三套完全独立的生成系统。
4. 不为了共享能力提前重构为通用多模态架构。
5. 不强制 Quick-A/B 执行 Listing 的 Planning。
6. 不允许模型自行创建或确认未知商品事实。
7. 一期默认采用 L1～L3，不以通用 Agent Runtime 或多 Agent 平台为前置；任务级 L4 必须有业务证据、完整契约与单独实施授权。
8. 必须保留既有历史 Task、版本和运行证据。

## 3. P0 开发范围

### P0-01：三个工作模式

目标 UI：

- 同款快速改版（Quick-A）
- 换主体快速改版（Quick-B）
- 商品资料制图（Listing）

当前代码据此前只读调查只有 `product_pack` 与 `quick_redesign` 两种任务模式。

实施时优先考虑保留现有内部业务模式、为 Quick 增加明确子类型，避免无必要的数据库或 API 全面迁移。

**验收：**

- 运营能明确选择三种入口。
- 创建任务后保存所选业务语义。
- Quick-A/B 采用各自的约束。
- Listing 保留原有文字输入。
- 历史任务不会因新增选项被错误解释或破坏。

**E0-R01｜共享输入与图位分类（USER-CONFIRMED / 工程待实施）：**

三个入口尽可能复用商品图片/参考营销图上传、`product` / `reference` 角色分离、任务内共享商品素材，以及 `main`、`dimensions`、`comparison`、`selling_point`、`scene` 五类图位。图位的启用状态、主要参考绑定、可选逐图要求和逐图尺寸可追踪；商品素材数量不自动决定输出数量。当前源码没有完整商品素材子分类，本次不将白底、细节、配件、包装等名称当作已实现能力，只保留尺寸专项素材所需的识别与关联。

- Quick-A/B 的场景身份必须明确保存，不能仅在 UI 显示，也不能依图片数量或内容猜测；不改变 Quick 无强制 Planning 的规则。
- Listing 采用相同图位分类体系，但保留商品文字资料、原有逐图 Planning 和人工确认。分类、参考和计划须正确关联，不破坏既有计划身份。
- 每个启用图位具有稳定身份、明确类型、一张本任务主要参考、可选要求、对应输出尺寸，以及独立生成/审核结果。同一主要参考的绑定唯一性规则保持不变，非法或跨任务引用须拒绝。

**E0-R02｜动态 N 图位与必要 P0 验收：**

卖点图、场景图按运营需求动态增加或删除 N 项，不保留旧 3/2 上限或总计 8 的固定业务上限，也不设替代的固定业务总数。主图、尺寸图、对比图各 max1；尺寸图仍须具备 P0-03 的真实尺寸白底专项素材。以下为工程验收要求，不是本轮已执行结果：

1. 同一任务至少配置并启用 **4 个 selling_point、3 个 scene，启用总图位超过 8 个**；4/3 和超过 8 仅为突破旧限制的最小样本，不是新上限。
2. 主图、尺寸图、对比图各超过 1 个时由服务端拒绝；尺寸图验收素材须满足 P0-03，不能用任意商品图冒充专项素材。
3. 删除中间图位后重新添加，不重编号剩余输出，不串参考、要求或尺寸；顺序明确且可恢复。
4. 保存、刷新、另存后，场景、启用状态、图位身份、顺序、主要参考、逐图要求和尺寸正确恢复；另存中的参考资产重映射须保持绑定正确。
5. 增加商品素材不自动增加输出图位；未启用图位不进入生成。实际请求保留商品与参考角色，不混入其他图位主要参考。
6. Listing 的图位、参考 ID、理解、逐图计划及确认版本正确对应；共享输入不绕过 Planning 或人工确认。
7. 每个图位可独立生成、修改和 Pass；实际请求包含本图要求及尺寸，修改父 Run、版本、去重、锁、失败保留和零自动重试不受破坏。
8. 最终 ZIP 只导出明确 Pass 的版本，数量、顺序及文件名唯一性正确；实验包与 Inspector 能追踪图位、实际输入、请求及结果，不伪造缺失信息。
9. 历史 Quick、已有 Quick V1、Listing 和 CLI 回归保持；工程验收使用隔离匿名数据及 SDK Mock，不能代替真实图片和运营验收。

**技术容量风险：**Listing 全量 Planning 会受参考数量、Context 大小和输出预算影响；动态 N 不承诺任意数量一次规划或一次批量执行成功。上传总量、单文件大小、单次模型输入、Planning 输出、单批执行预算及并发/超时/费用/资源保护必须标为技术约束。超大任务的技术保护或分批策略须依据实际能力另行核验，本次不预设新的硬编码数量上限，也不授权自动追加模型调用或重试。

**历史兼容与版本约束：**

1. 旧 Quick 不自动判定为 Quick-A/B，缺少新场景信息不得通过素材数量或视觉相似性补猜。
2. 已有 Quick V1 的 Slot ID 不重编号，不以当前显示序号替换稳定输出身份。
3. Listing 原有计划按 reference ID 关联；不强制改造成 Quick 的输出 ID 体系。
4. 新增分类关系采用兼容映射，素材、图位和计划身份不可混用；另存时相应引用须一起正确映射。
5. 旧确认计划、Run、Pass 保持原样，不为补齐新字段批量改写。
6. 任务输入改变时，旧确认不能被错误继承；保留已有输入版本和确认校验。
7. 新旧任务均保持可读取，缺失历史分类或授权信息不伪装为已确认事实。
8. 不要求原地增删已执行任务的图位，优先保留现有另存新任务的保护方式。
9. 历史 Evidence 不改写；本次目标不要求迁移整个 Task 数据模型或重建任务系统。

### P0-02：场景信息权限

**Quick-A：**

允许使用同款参考中适用于当前商品的参数和卖点。

**Quick-B：**

运营选择该模式表示相关营销信息适用，但必须以目标商品原图替换参考商品外观。

**Listing：**

商品信息主要来自运营提交的文字资料；参考新增卖点不能自动继承。

**验收：**

- 不再使用与新 Quick 规则冲突的“所有参考参数及功能一律禁止继承”策略。
- 三个场景的 Prompt / Context 具有正确的信息来源边界。
- 不擅自引入其他商品专属的品牌、包装和配置。
- 运营指定的必保留内容不能被无提示地删除。
- 存在关键事实争议时可明确反馈给运营。

### P0-03：尺寸图前置条件

尺寸图必须具备目标商品真实尺寸的已标注白底素材。

不得从参考图或商品外观自行补造尺寸。

**验收：**

- 未提供专项素材时，不能进入尺寸图生成。
- 运营能明确看到原因。
- 提供素材后可以执行对应尺寸图任务。
- 生成图必须接受真实数值及标注对应关系审核。

不要求系统通过图片识别独立证明尺寸数值真实。业务上由运营对所提供尺寸素材负责。

### P0-04：Listing 理解与确认

保留已有理解、Planning 和人工确认链路。

重点解决：

- 参考图内容理解明显错误；
- 当前商品图片与 Listing 显著冲突；
- 未经确认的参考宣称进入计划；
- 当前确认计划与最新输入版本不一致。

**验收：**

- 运营能看到相关制作方案和需要确认的异常。
- 显著冲突不会被静默当成正确商品事实。
- 未解决的争议宣称不能直接进入已确认制作方案。
- 运营确认后，实际生成使用对应确认版本。
- 不无故要求运营逐条重新核验所有无明显争议的 Listing 宣称。

### P0-05：Generation / Review / Evidence 闭环

继续复用现有生成、逐图修改、版本选择、人工 Pass 和导出流程。

重点补充必要的业务可观察性。

**验收：**

- 有效请求能够追溯使用了哪些商品素材、参考素材及制作要求。
- 能追溯对应的模式、图位和版本。
- 运营能够选择、修改和接受指定候选版本。
- 失败调用不会被伪装成完成。
- 已 Pass 版本不会被新候选静默替换。
- 实际图片及审核结果可追踪。

建议支持记录简洁的人工拒绝原因，例如商品外观、商品事实、参考适配、文字排版、设计质量等类别及可选补充说明。

一期不建设复杂自动评分平台。

## 4. AI 能力实施边界

| 能力 | 一期工作 |
|---|---|
| S1 商品理解 | 保留原生模型能力，处理必要的事实冲突 |
| S2 参考理解 | 改善输入角色与明显误读的处理 |
| S3 参考适配 | 落实三种场景的信息权限 |
| S4 渠道规则 | 仅针对实际指定且有可靠依据的规则 |
| S5 专业制作决策 | 使用现有模型，保留可选知识增强 |
| S6 Context Engineering | 确保实际有效输入、来源和版本正确 |

不得以“实现 S1～S6”为理由强制新增六套组件。

### 4.1 低自主度交付与可选扩展

自主度沿用 [04 架构候选](../04_AI_AGENT_SUITABILITY/IMAGE_AI_ARCHITECTURE_DECISION_V0.1.md#ai-autonomy-levels) 的项目工程分类，不代表统一行业标准或智能高低：

- **L1 Deterministic Rules：**确定性业务条件，例如缺少真实尺寸专项素材时不生成尺寸图。
- **L2 LLM Decision：**根据商品、参考与目标进行卖点、适配及制作判断，不要求动态工具调用。
- **L3 Conditional Workflow：**根据规则或模型结果进入既定分支，例如事实明显冲突交运营确认，资料正常时按原流程继续。
- **L4 Bounded Agent：**未来按需、单独授权的任务级扩展，可在获准目标、工具与预算内行动、观察和调整。
- **L5 Autonomous Agent：**更大范围的自主任务与工具协作，一期不涉及。

本契约主要采用 L1～L3。固定 Workflow 同样具有 AI 决策能力；普通 LLM 判断不自动成为 Agent。S1/S2 默认多模态模型，S3 默认模型加场景规则，S4 优先有来源的确定性规则查询，S5 默认 Model-first 加可选已审核 Knowledge，S6 默认可追溯的确定性组装；具体 Agent 候选条件见 04 第 5～6 节。

系统保留加入任务级 L4 的边界，不等于已授权开发，也不表示其为当前已有实现。本次一期契约不要求交付 Agent Runtime，不添加 Agent 成功率或 Agent 数量作为完成门槛，原 P0 业务验收条件不变。

### 4.2 Bounded Agent 的单独授权契约

后续 E 阶段只有在明确业务问题、简单方法存在可观察不足、必要工具操作及其结果确实影响下一步处理时，才研究 L4。还必须证明工具权限、执行预算、人工确认、停止条件、完整 Evidence 和评价方法可控制。

任何新增 Agent 任务必须先明确以下契约，再单独批准需求、工具范围、调用成本与实施：

| 契约项 | 最小要求 |
|---|---|
| Task Goal | 明确业务目标及完成结果 |
| Allowed Tools | 工具、资料访问、读写和付费权限 |
| Input / Output Contract | 输入来源和可检查输出 |
| Business Rules | 原场景业务规则及不可绕过条件 |
| Fact Permissions | 商品身份、外观和宣称使用权限 |
| Execution Budget | 调用次数、费用及资源边界 |
| Maximum Steps / Retries | 有限步骤和重试上限，保留已有付费操作保护 |
| Human Approval Conditions | 事实争议、方案确认及需另行授权的操作 |
| Stop Conditions | 完成、预算耗尽、资料不足或无获准下一步时停止 |
| Failure Handling | 保留真实失败和执行不确定性，不伪装成功或盲目重试 |
| Evidence / Observability | 实际输入、行动、工具返回、版本及人工操作 |
| Evaluation Criteria | 与简单方案对照的业务效果、风险及成本 |

Agent 不得自行改变运营选择的模式、商品 SKU 或身份，不得把未确认参考卖点或争议宣称升级为事实；不得绕过 Listing 计划确认、自动 Pass、未授权付费调用或无限重试。它只能在已有事实权限内选择方法，不增加业务权限，不把 Quick 改成强制 Planning。

这些要求不批准当前 Coding、付费调用、部署或通用 Agent Runtime 开发，也不自动将 L4 加入所有商品图任务。

## 5. 图片业务质量底线

### Quick-A

- 目标商品外观没有被错误改变。
- 使用的规格与卖点有业务依据。
- 设计有符合运营目标的差异化。
- 必保留信息得到处理。
- 运营实际接受最终成图。

### Quick-B

- 主视觉中的商品是实际待售商品。
- 局部特写、结构展示及场景主体不存在参考商品冒充。
- 没有混合两款商品的结构和标识。
- 沿用的信息对实际商品适用。
- 换主体后布局合理。
- 运营实际接受最终成图。

### Listing

- 商品资料及参考图得到正确区分。
- 关键事实冲突经过处理。
- 逐图方案经过运营确认。
- 最终生成与确认计划一致。
- 商品外观及宣称没有明显错误。
- 运营实际接受最终成图。

## 6. Evaluation 设计

一期分两层评价。

### 工程验收

检查：

- 模式与图位关联；
- 输入完整性与来源；
- 规则触发；
- Prompt / Context 实际传递；
- 状态与版本一致性；
- 请求和响应记录；
- 失败恢复及人工操作。

工程通过不等于业务通过。

### 业务验收

使用真实商品案例检查：

- 商品身份正确性；
- 宣称与资料一致性；
- 视觉设计适用性；
- 文字及布局质量；
- 运营接受或拒绝的原因；
- 修改次数和最终结果。

一期至少需要 Quick-A、Quick-B、Listing 各一条可完整追溯的真实端到端案例，并覆盖关键异常分支。

这只是最小交付门槛，不代表三个样本已经足以证明系统的总体成功率。

不预先编造接受率、成功率或成本阈值。先记录真实基线，再决定后续质量目标。

## 7. 建议实施顺序

### E0：代码现状与契约对照

针对本契约核对现有实现，形成最小差异清单。

不重做已经完成的全面架构调查。

### E1：业务规则与输入权限

优先处理模式信息、参考信息继承、尺寸素材前置、Listing 冲突及版本约束。

完成对应单元和集成测试。

### E2：三个工作模式体验

在保留已有内部业务能力的前提下，实现三个 UI 入口与对应业务行为。

确保 Quick 不被强制加入独立 Planning。

### E3：生成及审核闭环

核实实际生成请求、模式约束、图位、修改、Pass 和 Evidence 的一致性。

### E4：真实业务验收

分别使用三个真实场景完成端到端生成与运营验收。

记录失败原因、改动和结果。

### E5：Pilot

仅在本地功能与业务验收达到约定条件后，再单独批准部署到 Pilot。

不因单元测试通过而自动发布。

## 8. 明确延后

以下内容不阻挡一期：

- 正式 Knowledge 检索服务；
- 大规模制图知识卡库；
- 自动 Skill 选择；
- 通用 Agent；
- 多 Agent 协作；
- 自动运营决策；
- 完整图片自动质量评价；
- Photoshop 自动化全链路；
- 跨媒体系统重构。

这些作为后续可验证的候选能力，不作为一期开发任务。

这里延后的是上述通用平台和自动化，不是永久禁止任务级 L4；个别 Bounded Agent 是否引入，须依第 4.2 节另行取得证据与授权，不构成一期交付阻断项。

## 9. 开发过程约束

Codex 后续 Coding 必须：

- 在明确授权的任务范围内修改；
- 修改前确认 Git 和相关源码状态；
- 优先复用现有组件；
- 不擅自改写业务权威文档；
- 不修改历史 Run / Evidence；
- 不扩大为全仓重构；
- 保留可重复执行的工程测试；
- 区分 Engineering Verified 和 Business Accepted；
- 未经明确授权不部署、不执行付费生成实验、不 Commit / Push。

每个开发任务都应有明确的输入、允许修改范围、完成标准和验证证据。

## 10. Done 标准

一期只有在以下条件满足时才可报告业务交付完成：

1. 三种工作模式能够正确创建和执行。
2. 已确认的事实权限和关键业务规则得到落实。
3. Quick-A/B 和 Listing 的实际执行策略符合目标流程。
4. 三种模式都有真实生成与人工审核证据。
5. 关键异常不会静默进入已接受结果。
6. 版本、修改、Pass 和 Evidence 可追溯。
7. 运营确认对应交付图片满足实际业务需求。

如果工程测试通过但尚无运营接受图片，状态应报告为：

`ENGINEERING VERIFIED / BUSINESS ACCEPTANCE PENDING`

不能报告为整体完成。

## 11. 实施结论

一期以现有代码为基础，优先完成三个工作模式与正确业务约束，再开展真实业务验收。

一期以低自主度 AI Decision 与场景化 Workflow（L1～L3）为核心，保留按需、单独授权的任务级 L4；不预建通用自主 Agent 或多 Agent 平台。架构保留演进边界不等于实施批准，不改变原有 P0 与运营验收范围。

本契约不授权立即修改源码。后续 Coding 任务应在架构和契约获得最终确认后逐项启动。
